What was covered

Not tested, and why

  • Price slider upper bound (T29): the slider is a drag-only widget with no input for the bound. The defect is shown by request evidence in BUG-14.
  • Update profile and change password (T30): it would change the account every signed-in test shares during a run.
  • Contact form attachments (T31): needs fixture files, and lower value than the send path.
  • Admin area (T32): no admin account was available, and a self-registered customer cannot reach it.
  • Copy and spelling: reported once in BUG-15 rather than asserted in tests.

Notes on the environment

  • No test account was given, so the suite registers a fresh throwaway @example.test customer at the start of each run. No real personal or payment data was used.
  • Icons from cdnjs.cloudflare.com did not load because the browser is locked to the shop and its API. That is a setting of this run, not a bug in the app.
  • The first page load failed twice with an HTTP/3 (QUIC) network error and worked on the third try. That came from the network between this machine and the site, and is not counted as a bug.

BUG-01 My invoices returns other customers' invoices (personal data leak)

Severity: critical
Area: Order history / data isolation
Environment: https://with-bugs.practicesoftwaretesting.com, Chromium (Playwright Desktop Chrome), 1280x720

Steps to reproduce

  1. Register a brand-new customer and sign in.
  2. Open My account > Invoices (/#/account/invoices).
  3. Inspect the GET /invoices?page=1 response the page loads.

Expected

The response contains only invoices whose user_id is the signed-in customer's id (a new customer has none, or only the orders they placed).

Actual

The response contains invoices of other customers (other user_id values), including each invoice's billing address, city, postcode, country, payment method, payment account name and payment account number. During exploration a new account received 11 invoices, 10 of them belonging to other users. Personal details are deliberately not copied into this report.

Evidence

  • Failing test: account.spec.ts > "My invoices only returns the signed-in customer own invoices". Received foreign owner ids [4, 2, 3] for a freshly registered customer.
  • Screenshot / trace: test-results/account-Account-My-invoices-only-returns-the-signed-in-customer-own-invoices-desktop/ (latest run).
  • Exploration: journeys.md J2.

BUG-02 Profile API sends the password hash to the browser

Severity: major
Area: Account / security
Environment: https://with-bugs.practicesoftwaretesting.com, Chromium (Playwright Desktop Chrome), 1280x720

Steps to reproduce

  1. Sign in as any customer.
  2. Open My profile (/#/account/profile).
  3. Inspect the GET /users/me response.

Expected

The response carries profile fields only; no password or password hash ever leaves the server.

Actual

The response includes a password field holding the account's password hash (64 hex characters), plus failed_login_attempts. Anyone with access to the browser (XSS, shared machine, proxy logs) gets an offline-crackable hash.

Evidence

  • Failing test: account.spec.ts > "the profile data sent to the browser does not include the password hash" (expect(me).not.toHaveProperty('password') fails).
  • Exploration: journeys.md J5.

Test plan

Test plan: Practice Software Testing - Toolshop (with bugs)

Source: journeys.md in this run folder.

Approach

  • No shared test account exists, so auth.setup.ts registers a fresh throwaway @example.test customer through the UI at the start of every run, with a password generated in memory, signs in and saves the session to .auth/user.json. Signed-in specs opt in with that storage state. The credentials are never written to disk.
  • Specs that need their own login (register-then-sign-in) register their own throwaway account.
  • Every test asserts the correct business behaviour. Where the app is buggy the test fails and the failure is written up in bugs/; assertions are never weakened.
  • Expected totals are recomputed in the test from catalogue prices (Combination Pliers $14.15, Slip Joint Pliers $9.17).
  • Angular <select> controls ignore Playwright's selectOption in some forms (country, subject), so page objects pick options with the keyboard, as a real user would.

Journey map

Journey map: Practice Software Testing - Toolshop (v5.0 "with bugs")

App summary

An Angular single-page tool shop (hash routing, /#/...) used for software-testing training. Visitors browse a catalogue of hand tools, power tools and rentals (27 products over 3 pages of 9), search, sort and filter by category, brand, price and eco-friendliness, add to a cart, and check out through a 4-step wizard (Cart, Sign in, Address, Payment) that produces an invoice. Customers can register, sign in, manage profile, favourites, invoices and messages, and use a contact form. The front end talks to the API at api-with-bugs.practicesoftwaretesting.com. The banner says "Bug Hunting Mode": the build contains deliberate defects. Almost every interactive element carries a stable data-test attribute.

No test account was given in the task and the app does not advertise one, so I registered a throwaway account with an @example.test email. A self-registered customer has role user; no admin area is reachable from that role, so admin pages were not explored (see "Not explored").
